An `Effect[A, E, R]` describes a computation. Building one runs nothing; a **run function**
(`run_blocking`, `run_async`, `run_main`) executes it on a fiber.

<include meta='title="values.py"'>../../snippets/effects/values.py</include>

- `fx.succeed(value)` wraps a value; `fx.sync(f)` calls `f` each time the effect runs.
- `map` transforms the value; `flat_map` continues with another effect.

## Generators

Chains of `flat_map` get hard to read. Write the effect as a generator instead: `yield from`
an effect to get its value. `@fx.gen` makes an effect from a generator; `@fx.fn` makes a
function that returns one.

<include meta='title="generators.py"'>../../snippets/effects/generators.py</include>

<Callout title="A bare number is milliseconds">
As in Effect, `fx.sleep(2.5)` sleeps 2.5 milliseconds, and so does every other duration given as a
number. Write the unit, `fx.sleep("2.5 seconds")`, or a `timedelta`. See
[Durations](/docs/schedules#durations).
</Callout>

pyright infers the success type from `return`, the errors from every effect that can fail and
the services from every service used. You rarely write `Effect[...]` yourself, except on
function signatures you want to pin.

A generic function body is the exception: pyright loses its type parameter when the body also
uses other services, so annotate its return as `fx.Gen[A, E, R]` (what the body yields and
returns), as in `def with_scope[R](eff: fx.Effect[int, Never, R]) -> fx.Gen[int, Never, R | Scope]`.
`@fx.fn` raises `TypeError` for a generic body without a return annotation.

pyright widens a literal returned from a lambda: `eff.map(lambda r: r.answers[team].label)` is
an `Effect[str, ...]` even though the label is `Literal["billing", "tech"]`, and the same holds
for `Ok.map`, `fx.for_each` and every other combinator taking a function. A `def` with a return
annotation, or an annotated variable receiving the result, keeps the literal.

## Running effects

| Function | Use it for |
| --- | --- |
| `run_blocking(eff)` | scripts and tests: no event loop needed, sleeps and forks work |
| `run_sync(eff)` | an effect that finishes synchronously; anything else dies with `AsyncFiberError`, as Effect's `runSync` |
| `run_blocking_exit(eff)` | the same, returning an `Exit` (`Success` or `Failure`) instead of raising |
| `await run_async(eff)` | inside asyncio code |
| `run_main(eff)` | a program's entry point: handles SIGINT/SIGTERM, logs failures, sets the exit code |
| `ManagedRuntime.make(layer)` | building services once and running many effects with them (web servers) |

Every run function needs the service type to be `Never`, so a missing service is a type error at
the call site. `run_sync`, `run_blocking` and `run_async` also need the error type to be `Never`; their `_exit`
variants and `run_main` take an effect that can fail and hand you (or log) the failure.

An effect reads its caller's `contextvars`, as Effect's runs follow Node's `AsyncLocalStorage`:
a request id set by a web request's handler before `await runtime.run_async(...)` is the one the
effect, its forked fibers and its coroutines see, however many requests run at once. A fiber
resumes in the context it waited in, whoever wakes it.

`fx.from_async` and `fx.try_async` wrap coroutines; `fx.blocking` and `fx.try_blocking` move
blocking calls to a thread.

## Common mistakes

These run, or fail far from the line that caused them. Most are what a coroutine would do.

- **`time.sleep` in an effect** blocks the thread, so every fiber of the run waits with it and
  `.timeout` can't interrupt it. Use `fx.sleep("1 second")`, and `fx.blocking(f)` for a blocking
  call you can't avoid: it runs on a thread, and the fiber waits without blocking the others.
- **`run_blocking` in a coroutine or a notebook cell** blocks the running event loop until the
  effect is done, and warns with `RunBlockingInEventLoopWarning`. There, use
  `await fx.run_async(eff)`; Jupyter runs cells on an event loop, so `await` works at the top
  of a cell.
- **`yield eff` instead of `yield from eff`** runs the same, but pyright can't see the value or
  the effect's errors and services: the variable is `Unknown`, which strict mode reports. Always
  write `yield from`.
- **Calling a function and using what it gives as the result.** `greet("ada")` builds an
  effect and runs nothing: `print(greet("ada"))` shows `<Effect, not run: ...>`, and
  `greet("ada") + "!"` raises `TypeError`. Run it with `fx.run_blocking(greet("ada"))`, or
  inside a generator, `yield from greet("ada")`.
- **`eff()`** raises `TypeError: '_Succeed' object is not callable` (pyright reports it first):
  an effect is a value, not a function. Run it as above.
- **`await eff`** raises `TypeError: '_Succeed' object can't be awaited` (pyright reports it
  first): an effect is a description, not a coroutine. In a coroutine, run it with
  `await fx.run_async(eff)`; inside a generator, `yield from eff`. Effects are deliberately not
  awaitable, so libraries that await whatever is awaitable pass them through untouched.
- **`@fx.fn async def`** is not an effect body: pyright reports that no overload of `fn` matches,
  and running it dies with a `TypeError`. Write a `def` and run the coroutine inside it with
  `yield from fx.from_async(f)`.
- **`eff.catch_tag(...)`** raises `AttributeError`: `catch_tag`, `provide` and the other
  combinators that remove something from the type are functions for `.pipe`:
  `eff.pipe(fx.catch_tag(NotFound, handler))` (see [Typed errors](/docs/errors#handling-errors)).
- **`raise NotFound(...)`** in a generator is a defect, not a typed failure, so `catch_tag` never
  sees it. Fail with `return (yield from NotFound(...))` (see
  [Typed errors](/docs/errors#defining-and-failing)).
