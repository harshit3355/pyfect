---
title: Upgrading event log stores from 0.6.5
description: "SQL encrypted event log stores written by pyfect 0.6.5 or earlier, under a public key or store id with a '/': what changed, what the server does by itself, and when you act."
---

Up to 0.6.5, `sql_event_log_server_encrypted` named a store's tables after the text
`publicKey/storeId`, as Effect does. Two (public key, store id) pairs can share that text:
`("Kq9/xT2+bQ==", "main")` and `("Kq9", "xT2+bQ==/main")` both make `Kq9/xT2+bQ==/main`, so
they shared one store. From 0.6.6 each pair has tables of its own, and a store whose old
tables could belong to either pair has to be handed to the right one.

## Who is affected

Only the SQL storage of the encrypted server, `sql_event_log_server_encrypted`, on any
database. The memory storage and the unencrypted server are not affected.

Within it, only stores written by 0.6.5 or earlier whose `publicKey/storeId` holds more than
one `/`: a public key with a `/` in it, which standard base64 keys often have, or a store
id with one, such as `"notes/2024"`. A pair whose text has exactly one `/`, such as a UUID
key with the store id `"main"`, keeps its tables and needs nothing. So does a store with no
batches from 0.6.5.

## Symptoms

Under 0.6.6, an affected store did not open. Clients got an `EventLogProtocolError` with
code `InternalServerError` and the message "Decoding failure" (changes) or "Persistence
failure" (writes and the latest sequence), retried forever, and the server logged nothing.
Storage calls died with `LegacyStoreNeedsMigration`.

From 0.6.7 most stores open by themselves (below). One that still can't says so: the client
gets an `InternalServerError` whose message says the store waits for the server's operator,
with its `store_id` set, and the server logs a warning naming the store once.

## Stop every 0.6.5 node first

Stop every server running 0.6.5 or earlier before you start a newer one on the same
database, and don't go back to 0.6.5 afterwards. A 0.6.5 node writes a store under its old
tables while a newer node writes it under its new ones, so each sees only its own writes.

The two halves can't be merged. Each numbers its batches from 1, and clients keep their
place in the store by that number, so batches moved from one half to the other would land
below the place of clients that synced through the other node, and those clients would
never receive them. The newer version serves the new tables, logs a warning that the store
was split, and refuses to migrate it.

Upgrading from 0.6.6 to 0.6.7 can be done one node at a time.

## What the server does by itself

A key that wrote through a server has authenticated, and the server records every key that
has, in `<entry_table_prefix>_session_auth_bindings`. When an affected store is first asked
for, the server looks there at every key the old name splits into. If the asking key is the
only one that has authenticated, the store gets its old tables, and the server logs that it
did. Nothing else is needed: for most deployments the upgrade has no manual step.

## When you need to act

The server refuses a store, and logs why, in two cases:

- **Another key that splits the same name has authenticated too.** Either identity may have
  written the old tables, and the server can't read them to tell. Anyone can authenticate
  as a new key, so this is also what an identity trying to claim someone else's store
  causes. Find out which identity wrote the store (which of your users had data in it), then
  run `migrate_legacy_store(public_key, store_id, not_written_by=[...])` for that one,
  naming every other key the refusal lists. The call is refused if the list doesn't match
  what the bindings show.
- **The store's key never authenticated.** Only a store written without the server, straight
  through the storage, gets here. `migrate_legacy_store` refuses a key with no binding.

Refusals describe the store that asked, never a store to migrate. Don't migrate a store
because a log line names it: run the call for the identity you have confirmed.

`migrate_legacy_store` and `legacy_stores` take the storage's `entry_table_prefix` and
`remote_id_table` and need a `SqlClient` and a `Digest`. `legacy_stores` lists the affected
stores and where each stands: `"pending"` (migrates on its next request), `"ambiguous"`
(needs you, with the other keys), `"split"` (written by a 0.6.5 node after the upgrade),
`"migrated"`, or `"taken"`: another pair sharing the name was given the tables. 0.6.6 gave
them to whichever pair `migrate_legacy_store` named, so if you ran it under 0.6.6, check
every `"taken"` store whose identity you know wrote the data, and every `"migrated"` one
with `other_keys`.

## Store ids come from your app

The server never stored store ids, only a hash of each pair, so it can't list them.
`legacy_stores` takes the ids your app opens (often a few fixed names such as `"main"`) and
checks them against every key that has authenticated. A store id your app builds at run
time has to be listed the same way.

## Stores two identities shared can't be split

If two pairs that share a name both wrote under 0.6.5, their batches are in the same
tables, encrypted under different keys. The server can't tell them apart, so whichever pair
gets the tables gets both histories, and the other starts empty. Its entries survive only
in its clients' local journals.
